# WeWork DAG 管理与 Eval 设计 v0.1

日期：2026-09-12。状态：讨论基线，非已实现功能。来源：本次用户访谈；UI 接收任务为“规范化并设计 Wework UI”。

产品版本范围：基于现有 V2.0，完成 V2.1.0 的 DAG 能力调整并真实跑通后，再考虑 V3.0。本文件 v0.1 是设计文档版本，不是产品版本。只交接能力、语义和验收需求，不规定 UI 布局、控件、动效或具体交互方案；这些由用户与 UI 任务继续探索。

## 1. 目标与组织视角

WeWork 是 harness of harness，组织并运行不同形式的协作。输出可能是一次性交付，也可能是持续运行、迭代的自治工作组织；不是只做元评测工具。

DAG 首先是一种管理表示。上层节点代表助手在当前工作中的参与，边表示依赖与交接；助手内部允许拥有正在执行任务的运行 DAG。流程执行逻辑称为 Workflow，允许条件、重试、迭代。无需为管理而把每次 tool/work 调用拆成最小指令。

管理需要回答：事情如何发展、关键决策依据是什么、问题从哪里开始、谁受影响、谁负责协调；能发现共同迷失方向和共同接受错误方向两种情况。共识不等于正确，Eval 要引入独立验收依据。

与 2026-09-10 接管文档的协调：旧文档强调节点引用真实子工作，本轮强调助手视角。建议用“助手在某项工作/阶段中的参与实例”连接 employeeId 与 workId，而非复制工作状态，也不是一个助手全局只能有一个节点。这是待 UI/数据模型验证的兼容方案，不代表用户已确定底层 schema。团队仍可并发承接多项工作，画布切换不改变后台任务。

## 2. 采用、创建与复用

- 用户明确要求用或不用 DAG 时优先遵从。
- Skill 的建议是依据，仍需判断任务复杂度与适配性。Reference 是参考依据，不自动证明可执行；其独立触发条件尚未最终确认。
- 执行流程基本一致的任务出现至少 3 次，且具备值得管理的复杂度时，采用并沉淀 DAG。简单流程不因重复或 tool 数量而强制建图。
- 相同 Skill 是流程相似的强信号；同时考虑实际关键步骤与依赖。目的不同也可能共享底层流程；公共片段可以在自身满足条件时独立成为子 DAG。
- 单次 tool 调用通常简单；少量固定顺序调用、没有中间判断/并行/恢复需求，也可简单。封装内部复杂度不等于外部编排复杂度。不硬编码调用次数阈值。
- 现成、适配或高度相似的 DAG 可以首次直接复用，不必等三次。适配检查和差异记录仍需要。
- 路径、依赖或迭代组织实质改变，倾向保留两个相关流程；仅替换职责及输入输出兼容模块，倾向保持同一流程并记录可选实现。以上是探索原则，不是已经确定的固定判定算法。记录每次选用的实现及任务相关差异。

## 3. 共享与助手经验

流程库与助手身份解耦，在授权的组织范围内共享；流程出现次数可跨助手累计。每次执行关联具体助手、流程版本、任务和结果。将同类任务优先交给熟悉助手是分配偏好，不是硬绑定。

Adaptive 的成功经验属于“助手 × 任务类型/适配范围”，不能把别人的成功直接转换成本助手权限。成功要有验收证据，不能只计执行结束。三次流程出现与三次助手成功是两个不同计数；后者的具体晋级阈值属于初版实验策略。

## 4. 四档授权

Ask for approval < Adaptive execution < Approve for me < Full access。

| 档位 | 行为 |
| --- | --- |
| Ask for approval（默认） | 计划及执行范围需审批；批准后在范围内执行，不默认逐 tool 审批 |
| Adaptive execution | 按该助手的同类任务历史表现，在授权边界内扩大自主范围；经验不足时申请审批 |
| Approve for me | 不依赖历史次数，自动判断授权内常规动作；不确定或越界逐级上报 |
| Full access | 授权内充分自主；保留非破坏性、可恢复边界，不等于无限权限 |

用户主动设置非默认档位，或明确授权上级管理下级设置；助手不能自行晋级档位。全局、助手、任务支持分层配置，必须保留生效权限及来源。冲突合并与可授予权限的具体算法暂不定死。

管理层级不固定绑定档位：下级可以 Auto，也可频繁汇报。汇报不等于停止；请求判断只暂停有疑问的部分；越权动作等待批准。不受影响的工作继续。上级在自身授权内审批，拿不准再逐级上报，最终到用户。

第一版升级事项：改变目标/验收标准、突破预算或权限、无法判断的方向冲突、多次无进展或影响他人交付、破坏性或无法确认恢复性的动作。具体阈值交由 Eval 调整。

所有模式保存执行与介入记录：触发原因、证据、授权来源、调整前后差异、影响范围、恢复方式和验证结果。用户主要看到筛选后的关键决策、可选方案与推荐理由，不承担所有细碎决策。

## 5. 生命周期与历史

ARC 只管理活跃缓存；持久流程的保留与删除另行决定。综合再使用机会、任务价值、重建成本、周期、替代情况和引用关系。低频不等于低价值；明确日历优先，数据不足不强拟合周期或泊松过程。

区分“没有适用任务出现”和“适用任务反复出现但总被更好流程替代”；后者是更强的淘汰依据，也应排除检索遗漏。周期任务按自身周期衡量，应急任务可因重要性保留。

初版状态：活跃、冷存储、待删除。新版本仅在已验证适用范围内替代旧版本，各有优势则并存。历史保留替代关系、原因和评测证据；当前、里程碑、回滚和被运行/测试引用的版本保留完整内容。普通中间历史可归档压缩，失去精确复现能力必须明确。无引用、无保留要求的细节经观察期再按权限清理。永久删除不视为天然可恢复。

借鉴 Git 版本与分支，不预先绑定 Git。工作成果由助手在阶段完成时处理提交，用户无需掌握 Git。Save/autosave 不等于正式版本；用户要求暂不继续细化提交机制，不增加逐次人工批准要求。

## 6. 图与迭代的技术表示（待验证）

助手协作会反复交接，静态助手关系未必无环。建议保留助手视角，将运行图展开为按阶段/尝试递增的参与实例；反馈触发下一次尝试，不在同一执行 DAG 中造回边。Workflow 可表达循环。UI 不应以 DAG 无环约束阻止真实返工；具体展开交互由 UI 任务探索。

## 7. Eval 与交付顺序

1. 先下载 1–3 条现成 multi-agent benchmark 样本，通过现有 WeWork runtime 跑通组织、执行、交接、持久化及结果检查。不追求榜单领先，不以 mock 成功冒充真实运行。
2. 经营报告作为完整、长程压力测试；需真实做出报告，先不用为它阻塞 benchmark 跑通。
3. 视频写作/协作作为真实成果交付目标，内容、素材与成品标准需要另行收集；不擅自缩成 benchmark。
4. 后续扩展 benchmark 评测，比较单助手、多助手自由协作和 DAG 管理，预算/模型/工具/信息条件可比。

WeWork 不是只做 benchmark 的框架。基础链路跑通不等于管理机制优于基线，更不等于经营报告或视频成果已完成。

质量先达标，再比同任务成本、端到端时间、关键路径、重试/协调成本及人工介入；按任务复杂度分层。工具时间拆分执行、排队、恢复，保留真实体验与受控对照，不用“时间除以难度分”代替评估。

基础 harness 测试选固定非 Adaptive 档位，冻结配置并隔离历史状态。自适应、复用、ARC 另用有顺序的任务序列测评，固定初始历史与时间，避免变量串扰。检查重要问题漏报、无谓审批、共同偏航发现率、纠偏效果、低频重要流程误删和无用流程清理。

首批核查来源（仅资料核查，尚未跑通）：
- MultiAgentBench / MARBLE：https://github.com/ulab-uiuc/MARBLE ，https://arxiv.org/abs/2503.01935
- AWS 企业协作场景：https://github.com/aws-samples/multiagent-collab-scenario-benchmark
- COMMA：https://github.com/tossowski/COMMA
- CORPGEN：https://www.microsoft.com/en-us/research/publication/corpgen-simulating-corporate-environments-with-autonomous-digital-employees-in-multi-horizon-task-environments/
- UCI Online Retail II：https://archive.ics.uci.edu/dataset/502/online%2Bretail%2Bii 。真实交易数据，无现成经营报告答案和完整业务因果说明。

## 8. UI 需求交接

基于现有 V2.0 产品做 V2.1.0 调整，不另造孤立应用，不推进 V3.0。本节仅约定信息与能力需求；具体表现形式、导航和布局由用户与 UI 任务探索，不预定画布、抽屉等组件方案。

职责：本 DAG/Eval 任务负责生成、采用、匹配复用、调整/版本、执行依赖、持久化、权限判定/上报及评测；“规范化并设计 Wework UI”负责前端输入、呈现与交互绑定。前端不另建生成策略或调度状态源。

用户补充确认：派活像聊天一样输入文字、粘贴问题、拖入或粘贴截图与材料；不要求额外表单或先手工建 DAG。材料进入实际附件存储后通过引用传递，不能假定客户端路径已可被执行器读取。服务接收消息和材料后决定直接执行、复用、生成或请求必要澄清/审批。

接口语义（待核对现有 API 后落实，不代表新接口已经实现）：输入包含团队/会话、幂等请求标识、文本、附件引用和可选目标上下文；读取与事件提供工作、助手参与实例、依赖、运行版本、权限来源、阻塞/审批和成果引用；用户可补充、审批/拒绝、选择方案、调整授权、暂停/取消/恢复和验收。变更在服务侧重新校验权限及版本，刷新后从持久快照恢复。两端先复用现有 Host/服务接口再补缺口。

- 上层从助手看工作参与、依赖和交接，允许进入助手当前任务的运行图，再返回；同一助手允许参与多个任务/阶段。
- 关联同一真实工作状态；保留已有工作层级、跨任务负载和资源约束，避免助手图与任务图成为两套冲突数据库。
- 同时呈现现在的状态与事情如何发展；关键决策/依据/异常/调整/验证可追溯。
- 区分正常执行、等待交接、等待判断/审批、阻塞、纠偏、送审和真正完成。详细状态映射由实现确认。
- 显示四档授权、生效范围/来源；Adaptive 显示与本任务相关的经验依据。明确“已汇报但继续执行”与“等待审批”的区别。
- 上报提供问题、证据、影响、选项与建议；用户可下钻但无需审阅所有执行噪声。
- 流程库独立于助手，显示复用来源、版本关系、可选模块及本次差异；区分模板、运行实例和成果版本。
- 生命周期可解释，冷存储不显示成已删除；保留周期/重要性标记、历史清理影响及测试版本引用。
- 模拟数据与实际运行严格区分；尚未实现的 Adaptive、ARC 等不能显示为真实生效能力。

## 9. 后续需要验证，而非继续阻塞访谈的事项

相似度与复杂度阈值、模块替换兼容检查、经验升级/降级阈值、权限配置冲突、周期预测、历史保留期限、图中迭代展开，均以本版原则为实验基线；不能宣称这些算法已经确定或实现。
